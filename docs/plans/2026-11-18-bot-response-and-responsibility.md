# Bot 的自动响应与职责预设

- 日期为 2026-11-18，待维护者审阅。
- 本提案调整[群聊](2026-10-07-group-chat.md)和[Bot 之间派活](2026-10-16-bot-handoffs.md)中曾取消的上限，并沿用[角色与权限](2026-10-07-roles-and-permissions.md)的授权边界。

## 为什么

审查和修复反复转交时，单次回复可能看起来有用，整个任务却无法结束。进程重启后也必须认得已经投递的事件和已经尝试的审查问题。用户需要能分别设置谁可以唤起 Bot、Bot 承担哪些任务、工具可访问哪些资源。

## 提案行为

- 用户可以在 Bot 或群的 Responding to Bots 中选 Off、Selected Bots 或 All Bots。选择名单基于 Bot ID。群里开工须通过收件 Bot 与群的设置。旧团队保留原来的收件人默认规则，同时受共用的去重、审查与预算约束。用户直接输入也适用原来的路由。
- 每件任务允许最多八个 Bot 触发的回合，同一条调用链最多六跳。群里的分支共享任务额度。转交或结果触发下一位 Bot 时增加一跳。对同一工作的自动续跑使用一次回合额度，并保留原跳数。新的用户输入与用户授权的每次定时触发各有任务范围。
- 发送前在团队状态中写入事件标识、任务额度和审查问题次数。已有稳定的工具调用 ID、请求名或群帖子标识时，重复事件不触发第二次。DSH 重启后恢复等待中的消息时，核对原会话记录、收件箱、原有额度和当前设置。模型读取收件箱前再次检查当前设置。已接收的结果仍可从交换记录或群记录阅读。禁止自动启动时，结果只进记录。
- Bot 在群内发送请求时，回执只确认请求已记入群聊。实际开始前重新检查策略。运行前持久记录事件已被接收，重启时即使无法读取会话日志也不会再次触发。群目标的自动检查沿用当前任务的回合额度，只有群和收件 Bot 都允许所有 Bot 或使用旧默认时才能自动进行。用户在面板直接开始准备或恢复群目标时沿用用户入口。
- 自动审查修复由 `review_fix` 及 PR、提交 SHA、问题 ID 标识。建议发件方使用含仓库的 PR 标识、完整 SHA 与审查报告里的稳定问题 ID。审查 Bot 发给编码 Bot 的自动派活、显式修复请求、部分填写的问题字段及文本中明确的审查修复请求都要求完整身份。同一个问题最多两次自动尝试，内容相同的重试会被拒绝。
- Role & Communication 提供 Coordinator、Coding Agent、Code Reviewer、Research + Coding 与 Custom。团队示例是 Main Bot、审查 Bot、编码 Bot 与调研 Bot。协调员建议来自 Main Bot 或群管理员身份。选择模板先填编辑框，点击 Apply 才写入。回到 Custom 时还原保存的自定义指令和类别。
- 类别用于约束传入的自动任务。Bot 的直接派活和群发帖通过 `task_category` 声明类别，自动审查修复走 Coding，无分类的自动消息走 General。职责设置独立于 Main Bot、管理员、工具、文件系统、合并与推送权限。仅用户可应用或调整类别。
- IM 忽略平台标记为机器人或应用的消息，收件事件有平台消息 ID 时持久去重。配对手机只通过用户输入接口发消息。Bot 在自动回合或定时回合内无法新建或修改定时任务。只读窗口（团队在别处打开）不会启动回合，会直接回复用户说明消息没有送达，也不写回执，稍后重发仍可正常接收。

## 已知限制

- 持久记录采用保守的投递语义。如果主进程在保存额度后、写入收件箱前终止，或写入已接收状态后、模型开始前终止，可能用掉一次额度而没有执行。
- 路由记录按最近使用窗口保留：已完成的投递事件保留最近 1000 条，任务预算 4000 个，审查问题 2000 个。未完成的记录（等待投递或已派发）永远不会被清理，所以重启仍能完成已经授权的回合。被清理的事件对应的 routing 会被 `permitted` 拒绝，不会再启动回合；任务和审查记录随使用刷新顺序，处于对应事件的清理窗口之后。
- 已存在的 DSH 定时任务只有 `schedule` 来源，不能恢复它们原先由谁创建。IM 对平台未标明身份的账号沿用配对检查。
- 审查问题由调用方提供结构化身份，本地检查不查询 PR 服务。别名、不同长度的 SHA 或虚报问题 ID 无法统一核验。任意文字中的隐晦指令也无法可靠识别。
- 原来版本已生成的收据按原记录回放。已在旧版本启动且来源信息不足的回合只能按已有会话记录恢复。

## macOS 安装审阅

1. 审阅本提交后，在 Apple Silicon 与 Intel macOS 环境分别从同一源码构建 arm64 与 x64 ZIP。使用现有 `app` 的 `npm ci`、`node scripts/seed-electron-checksums.mjs`、`npm run dist` 及 `node scripts/check-packed.mjs`，校验打包的插件与生成的客户端属于同一提交。现有构建配置采用临时签名的 ZIP。发布下载前须用拟分发的成品核验 Gatekeeper，当前配置没有 Developer ID 签名和公证。
2. 在相应架构的隔离账户或虚拟机解包。使用独立的 `DS_BOT_HOME` 和 `DS_BOT_SHELL_DATA`，让 DSH 工作在测试目录，用 mock 模型和复制的测试团队验证职责设置、关闭自动响应、八回合与六跳、完整退出再启动后的去重和审查修复，以及结果可读。先完成打包完整性和 Gatekeeper 启动检查。
3. 验收并获得安装确认后，完全退出现有应用，保留此前的应用包，按应用 `locations.json` 的 `dataDir` 备份实际 DS Bot 数据（默认 `~/.ds-bot`）和 Electron 的应用设置，再用匹配架构的应用包替换。更新后验证队伍、会话和新设置。需要回滚时，完全退出并恢复应用包和同一时间点的数据快照，另存验证期间新增的数据。
