# 通知里直接答复

- 日期：2026-10-31
- 相关：#735、#736 的注意力通知；[桌面应用](2026-10-16-desktop-app.md)、[角色与权限](2026-10-07-roles-and-permissions.md)

## 为什么

注意力通知原来只在正文里说事件种类（如「等你批准」），用户必须回到应用才能知道在等什么、并答复。用户在桌面应用外（最小化、全屏做别的事）时，最常等的就是审批和问题卡：审批要知道 Bot 要做什么，问题卡要能直接选或输入答案。所以通知要带上足够的信息，并在能答复时就地答复。

## 已定的行为

- **群聊成员的审批**：正文显示工具、命令或路径、原因（各段裁剪长度，避免通知过长）。通知带「允许一次」「拒绝」两个按钮，点了就是聊天里同一个答复。
- **Bot 自己聊天里的审批**：正文显示同样的细节，但答复由 DSH 的审批卡负责，DS Bot 拿不到那个答复权。通知不带按钮，正文写明「在聊天里答复」，点击打开聊天。
- **问题卡**：正文显示问题和一行说明。单选的选项：Windows 上不超过三个用按钮，超过三个用一个下拉（`selection` action，自带提交按钮）；其他系统都用按钮。Bot 允许自定义答案（`allowCustom`）时带输入框，输入的文字作为 `custom` 答案。多选无法在通知的按钮或下拉里表达，正文注明在应用里选；`allowCustom` 时仍可输入。
- **视图、密钥卡、失败**：维持只说明种类。密钥卡尤其不能带内容。
- 答复与聊天共用同一个函数（`rt.answerApproval`、`rt.answerQuestion`）：卡还在、id 匹配、答案合法才生效，成功后清卡。通知只知道点的是第几个选项，内容由 Host 按原卡解析，通知不直接改状态。
- 答复经 Host IPC 往返：主进程发 `ds-bot:attention-answer`，Host 处理完回 `ds-bot:attention-result`。失败（卡已关闭、空答案、团队没在运行）时再弹一条通知说明原因，不静默失败。
- 同一事件只提醒一次（按 id 去重，沿用原规则）。点击通知仍然打开它所属的聊天（群审批回群）。

## 设计变更，需要维护者确认

#736 的设计文档写的是「通知正文只说明事件种类，不含任务内容」。这里改的是审批和问题卡两类：为了就地答复，正文引用工具、命令、问题与选项。其余种类维持原样。

代价是任务内容会进入系统通知中心（Windows 操作中心、macOS 通知中心），锁屏上可能可见；命令里也可能有敏感参数。如果维护者认为不可接受，正文策略集中在 `app/src/completion-notices.mjs` 的 `bodyOf`，可以只保留「种类 + 去聊天里答复」。

## 平台约束

- Windows：一条通知最多三个按钮（按这个上限设计），超过即改下拉；`selection` 的默认选中项 Electron 未写明，所以第一次事件里 `selectionIndex` 为 -1 时按「没选」处理，不下发空答案。
- macOS：按钮和输入框都支持；按钮超过三个时只在悬停里展开。
- Linux：Electron 的 `actions` 和 `hasReply` 只标注 darwin/win32，通知服务器也不一定支持按钮；最低保证是正文 + 点击打开聊天，答复仍在应用里完成。
- 所有平台的答复都经 Host 校验，通知只是入口。

## 隐私与安全

- 密钥卡的通知从不显示变量值或用途以外的内容，保持原状。
- 审批命令裁剪到 120 字符，原因 120，问题 160，选项标签 60；自定义答案只发给 Host，不写日志。
- 通知答复不新增权限：能点通知的只有本机当前用户；答复在 Host 内按原卡校验，重复答复被拒。
