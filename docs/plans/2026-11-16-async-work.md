# Bot 异步工作：前台始终能接话

- 日期：2026-11-16
- 相关：#783（改了它的决定）、#798、#1501 / #1548（同一 Bot 的并行会话，已撤回）

## 为什么

一个 Bot 的一段会话既聊天又干活。干长活时，人说话要么排队，要么插话打断：私聊里插话会取消正在进行的模型调用，被打断的活能不能接着做，要看模型自己记不记得。除了 shell，长时间的工具调用（浏览器、网页、MCP 等）也会卡住这一步，这期间谁说话都要等。

大家都找的角色（审查、校验）因此成了单车道：同一个 Bot 一次只做一件事。

取舍：

- 工具超过等待时间转后台仅作用于 shell 命令（DSH 原生后台 job），不用于改写用户发送消息的意图。
- 普通 Bot 私聊坚持「发送决定消息何时读，转后台决定旧活在哪里跑」：`steer` 纠正当前进行中的工作，`queue` 等待当前轮次结束后顺序处理，只有用户明确执行「将当前工作转到后台」（桌面/Web 按钮、IM `/background`）才将当前前台轮次整段移入后台任务并 fork 新前台；隐藏的同伴 Bot 工作轮在用户发言时仍自动隔离到 `bot-handoff`，同伴遇忙派活仍直接开轻量后台任务。
- 后台的活是 DS Bot 自己的会话和 DSH 的后台 job，用户看得见、停得下，换段和重启都不丢。所以仍然不用 DSH 的子代理（#798 的原因仍成立）。

## 已定的行为

### 前台和后台

- **前台**：Bot 和人说话的会话（私聊的当前段）。
- **后台命令**：shell 命令超过等待时间还没完成，就作为这段会话的后台 job 接着跑，这一步马上往下走。完成时结果回到会话：会话空闲就开一轮，忙就并进下一步。Bot 可以用 `job_kill` 停它。
- **后台任务**：同一个 Bot 的另一段独立会话（存放在 `bot.tasks[]`；不是 #1548 已撤回的可切换并行聊天），拥有跨换段不变的稳定 `taskId`。用 `task_start` 在父会话体量较小时（默认不超过 600 条事件）从最近已完成轮次 fork 分出；当父会话较长、首轮无已完成轮次、指定独立 `workdir` 或本地 CLI Agent 时，直接开轻量新会话，附带保留 `[Handoff]` / `[Checkpoint]` 结构的近期摘要，并将父前台段记入 `inheritedSegments` 供 `read_own_chat` 按需检索。通过 `rt.deliver` 投递与汇报，用 `task_send` / `task_stop` / `task_list` / `task_read` 管理。
  - **显式将当前工作转到后台（`fg-handoff`）**：普通私聊中用户发送新消息不再隐式触发换轨——`steer` 走当前轮插话、`queue` 排队等待当前轮完成。用户需要把正在运行的轮次移到后台、立即腾出前台聊别的事时，可在桌面/Web 活动行或输入框 `+` 菜单点击「将当前工作转到后台」（或在 IM 发送 `/background` / `/bg`），正在跑的这一轮整段保留移入 `bot.tasks[]`（`origin: 'fg-handoff'`），前台从上一已完成轮次 fork 出新段（保留 KV cache 与输入框未发内容），正在跑的工具调用和审批随后台任务继续；本地 CLI Agent、存在未决交互卡或排队用户消息时禁止移交。
  - **隐藏同伴轮自动隔离**：若前台正在执行对用户不可见的同伴 Bot 委托轮次，用户发送消息时仍自动把该隐藏轮移入 `bot-handoff` 并在新前台承接用户消息（本地 CLI 不可移交时将用户 `next-step` 降级为 `next-turn`），确保用户发言不注入或泄漏到同伴回复中。
  - **同伴 Bot 遇忙直开后台任务**：别的 Bot 发来 `message_bot` / `delegate_work` 请求而目标 Bot 前台正忙时，直接为该请求开轻量独立后台任务（`origin: 'bot-handoff'`，一律不 fork 目标 Bot 无关的前台用户会话，兼顾启动速度与隐私隔离，仍保留长期记忆与 `read_own_chat` 检索能力），不切走用户正在看的前台，完成后沿 `handoffs.js` 派活树回传请求方；前台在处理外部 Bot 派活时主动调 `task_start` 开后台任务，同样自动挂入 `handoffs.js` 派活树等待收齐后再交回上游。
  - **群聊内后台任务**：群成员可在群内调 `task_start` 开启挂在该群（`roomId`）下的后台任务，继承群的工作文件夹、权限与群记忆，按 `(bot, roomId)` 隔离；审批携带 `roomId` 冒泡到群顶栏、手机与 IM；完成后回报群聊并唤醒群批次；删群、踢人或停群时自动清理对应任务。
  - **只读查看与交互界面**：后台任务不切入前台，任务阅读器对用户只读，`bot-task-read` 按任务起始 `startSeq` 只返回该任务自身的指令、步骤、追问与回复（不混入继承的前台历史）。桌面端顶栏默认以紧凑单行灵动岛芯片呈现，悬停展开任务条、点击展开液态玻璃卡片（支持左右翻页、直接审批、通过 `bot-task-send` 发送追问、停止与跳转详情），详情抽屉提供独立 `Tasks` 标签页与右栏只读阅读器；侧边栏显示活跃任务计数胶囊；手机端在聊天顶栏提供活跃任务条、审批与停止入口。
  - **扁平两层与安全边界**：后台任务内禁止嵌套 `task_*` 工具，并禁止直接弹出 `ask_user` / `show_view` / `request_secret`（由任务回报前台统一向用户询问再经 `task_send` 转达）；工具审批直接归 DS Bot 托管并携带 `taskId` / `taskTitle` 冒泡到前台、手机端与 IM；持久化捕获发起时的 IM 来源（`imOrigin`），后台做完回报前台汇总后准确回传原 IM。
  - **重启后对账**：崩溃时正在跑轮次的由 `resume.js` 续跑、等外部 Bot 的继续等、等内存后台命令的自动标 `interrupted` 并汇报前台，不留僵尸任务。
- 其他工具调用不单独转后台：需要把非 shell 长工具移到后台以腾出前台时，由用户显式点击「将当前工作转到后台」，正在跑的工具调用随它一起在后台继续。

### 等待时间

- 默认 5 秒；设置 → 通用 → 高级 →「命令转后台（秒）」可以改（0 到 600 秒，0 表示一律马上转后台）。
- 只在 Bot 自己的会话里生效；群里的会话照旧（群有自己的轮次和批次规则，见[群聊](2026-10-07-group-chat.md)）。
- 正常路径复用 DSH 原生机制：0 秒直接以 `run_in_background: true` 启动，大于 0 秒将 `timeoutMs` 收紧到等待时间交由 DSH `waitOnJob` 原生晋升并由 `tool-jobs` 统一负责输出读取与完成通知；当会话已达后台 job 并发上限时不收紧 `timeoutMs`，避免降级前台模式后提前杀掉命令。审批等待不计入命令等待时间。

### 改了哪些已定的决定

- #783 定的是「并行只靠多个 Bot，Bot 内不开短期 Worker」。现在改为：一个 Bot 可以开自己的后台任务；多个 Bot 分工照旧。

## 不做什么

- 不把每个工具都包成后台 job：DSH 的 `tools/execute` 包装做不到（流水线把调用方的信号合进工具体，调用结束后工具体不能继续跑）；在会话作用域重新注册工具又会绕过按 Bot 关掉连接器、按会话过滤结果、MCP 的图片附件这些规则。前台空出来靠整段转后台任务。
- 不解禁 DSH 子代理。

## 已知限制

- 本地 Agent 的 Bot：CLI 内部的工具调用由 CLI 自己管。
- DSH 的本地 job 注册表默认每个会话最多同时 10 个 job。
- 设置较大等待时间并在期间被用户插话提前转后台的极少数场景下，若模型在原等待时间内调用 `job_output(wait: true)`，命令提前结束时可能因底层原生等待收尾移表而报 `unknown job`，命令结果仍由兜底完成通知送达。
- 等待时间设得很短时，如果命令在沙箱准备或子进程启动阶段就已超时，DSH `waitOnJob` 会按准备超时终止命令，不会转后台。
- 等待时间较长且用户中途插话拆离时，底层原生等待仍在继续；若命令在原等待时间内结束，完成通知由 DS Bot 兜底送达，但原生等待收尾时会从注册表移除该 job，之后无法再用 `job_output` 重读。
