# Bot 之间派活：状态、协议原语与 SQLite 协调总账

- 日期：2026-10-16
- 相关：#262；取代 #95（PR #136）的未读上限、#129（PR #166）的跳数上限和全团队 40 条上限，以及 Bot 在一个群里最多发起 3 轮的上限；群里的活见 #165（PR #257）
- 一起改：[群聊](2026-10-07-group-chat.md)「Bot 发起的轮次和回报」

## 为什么

Bot 之间派活原来按数量拦，不看对方的状态：

- **Bot 看不到对方在做什么。** DS Bot 为界面记录了每个 Bot 的状态，`list_bots` 却只给名字、角色、模型和文件夹。只有派活发出以后，结果里才有一两句（在忙 / 等批准 / 几条没读）。
- **刷屏按长度和总量拦。** 消息链 6 跳截断、全团队 40 条上限、固定返工步数上限不分正常推进与无进展空转：每一步都在产出新结果的合法长链会被误截断，而绕圈空转却要白耗多轮。
- **派出去的活，结果交不回来。** 如果派活树、等待关系、去重键和未读消息分散在 `state.json` 与进程内存队列里，遇到并发多方委派或宿主重启极易出现丢结果、双投递或串台。

取舍：

- **三层解耦**：展示层（`pair-*.jsonl` / 群账本 / 界面状态）只管呈现；协调总账（`<home>/coordination.sqlite` 五张表：`works`、`calls`、`inbox`、`waits`、`ready`）原子管理派活树、等待图、入箱消息与就绪队列；执行层（`dsh-adapter.js`）按优先级泵送并兼容 DSH D1–D4 原生能力与 `0.2.2-rc.5` 降级。
- **结构性防错 + 硬信号判停，不设硬编码步数上限**：系统只拦截结构上必然死锁的等待图成环（`call` 环与 `ask` 环），并以确定性硬信号检测无进展空转；只要有真实推进，任意长度的多 Bot 协作链都持续运行。
- **零唤醒静默与单次结算**：`note_bot` 和 `cancel_work` 静默留痕永不唤醒模型；每个 `call` 在 SQLite 单事务内最多结算一次，迟到结果自动归档，绝不重复触发回声。

## 已定的行为

### 协作原语（Call & Return）

Bot 间协作通过显式原语驱动，所有状态变更均经 `<home>/coordination.sqlite` 原子提交：

- `delegate_work`：向同伴发起委派，创建或复用带短编号 `#W…` 的 `works` 与 `calls` / `waits(kind='call')` 记录，并按目标当前状态自动决定复用前台或开独立隔离的 `bot-handoff` 后台任务会话（当目标前台忙或已有其他非前台活跃工作绑定在该前台会话时自动物理隔离，防止多方委派串台）。
- `ask_back`：受托方在执行中需要信息时向派活方发起阻塞追问（写入 `waits(kind='ask')` 与目标 `inbox(kind='ask')`），并通过 DSH D4 确定性让出当前回合（`yieldTurn`），不占用执行位。
- `answer_work`：派活方答复追问（写入 `inbox(kind='answer')` 并原子解除 `wait(kind='ask')`），受托方在全部必需等待结清后自动恢复执行。
- `cancel_work`：撤回未结案的委派，原子将子工作结案为 `stopped`，中止对应在跑回合或后台任务，并通过 DSH D1 零唤醒注记（`appendNote` / 降级 `pre-step` 附带）静默记录取消原因，永不唤醒目标。
- `note_bot`：向同伴发送单向静默备注，仅通过 DSH D1 写入目标 `inbox(kind='note')` 并附着于目标下一次真实唤醒的回合中，永不写入 `ready`、永不单独触发模型调用。
- `stop_bot`：叫停目标 Bot 并静默记录原因，不再唤醒被叫停 Bot 回复确认。
- 已结案结果的防回声约束：私聊里已结案的 `W…` 结果可以让派活方给用户做一次汇总，但它本身不是新的委派。只因这条结果醒来、没有上游待办时，若确实要开启下一件独立工作，必须在 `follow_up_to` 引用本回合收到的工作编号；引用不对不投递、不创建空待办。用户主动说话或继续尚未结案的上游工作不需要这个编号。
- 静默退场：Bot 触发的私聊回合（如收到已关闭工单通知）若无需向用户汇报，支持回复 `[PASS]` 或静默退出并自动收进 `exchangeTurns`，不在主聊产生空确认气泡或无效推送。

### 状态与展示

- 每个 Bot 的实时状态由宿主结合内存执行态与 `coordination.sqlite` 快照统一聚合（只读窗口同样可直接读取只读快照），优先级从高到低为：

  | 状态 | 条件 | 附带的信息 |
  |---|---|---|
  | 等用户批准 | 有一条未决的 `waits(kind='approval')` | 在哪里、等了多久 |
  | 换新会话中 | 正在写交接、换到新的一段 | 在哪里 |
  | 在干活 | 私聊、后台任务或某个群里有在跑的回合 | 在哪里、做了多久、正在做什么、为谁做 |
  | 在等别的 Bot | 存在未决 `waits(kind='call' \| 'ask')` | 在等谁（Bot 或群）、为谁做 |
  | 空闲 | 都不是 | — |

- 另外两项和状态一起给出：未答的问题/视图/密钥等待卡（`waits(kind='user_question' | 'secret')`）与未读入箱条数。
- `list_bots` 每个 Bot 一行，带上上述实时状态；状态不写进系统提示以保持前缀缓存稳定。
- 界面上，Bot 的形象动画与侧栏状态同步展示「在干活 / 等批准 / 在等别的 Bot（等 X 交回）/ 已暂停」。

### 作用域内修订与去重（`request_id`）

- **中途修订**：对已有活跃委派发送修订说明时，写入该工作 `inbox(kind='revise')` 并递增 `revision`，不破坏既有派活树结构；若目标在结束前恰好有新修订入箱，SQLite 乐观版本检查会阻止提前结案并自动重排让目标读取修订后再交卷。
- **请求身份（`request_id`）**：
  - 调用方传入可选 `request_id` 时，由 `requests.js` 在调用方专属锚点工作的 SQLite `inbox.dedup_key` 持久化指纹（发活方 + 场合 + `request_id` + 目标与正文摘要）。
  - 同名同内容直接重放原回执不重发；同名不同内容直接拒绝；投递中途状态未知时标记 `uncertain` 禁止盲重发；不按时间或条数淘汰，Bot 删除重建后随新 id 重置。

### 派活树、单次结算与放弃等待

- **派活树**：受托方 B 在处理 A 的工作期间继续派出的子委派（含 `task_start` 后台任务与 `post_to_group(report_back: true)` 群汇报）全部通过 `calls` 与 `waits(kind='call')` 挂在 B 的当前工作下。所有必需子等待结清前，B 的工作处于 `waiting` 状态不提前向上交卷；全部结清后 SQLite 单事务唤醒 B 汇总，连同子结果一并交回 A。
- **单次结算与迟到归档**：每次 `settleWork` 在 SQLite `BEGIN IMMEDIATE` 事务中原子写入终态（`done` / `failed` / `stopped`）、写父工作 `inbox(kind='result')`、关闭对应 `wait` 并在父工作所有必需等待归零时插入 `ready`。全文结果落盘于 `bot/handoff-results/`，对话日志按幂等去重同步记录 `pair-*.jsonl`。已取消或已结案工作的迟到结果自动归档，不重新唤醒主线。
- **崩溃安全对账**：投递前先在 `works` 登记确定性 `active_delivery_key`。宿主重启时，通过 DSH D2 冷读对账：未送达的精确补发一次，已入队的原地唤醒，已消费且工具中断或日志损坏的置为 `needs_verification` 可见暂停，已完成的直接结案唤醒父工作。旧版 `state.json`（`state.works` / `roomReports` / `roomBatches`）与 `inflight.json` 在首次启动时一次性幂等迁移入 `coordination.sqlite`。
- **放弃一条等待**：Bot 处于等待状态时，右键菜单支持针对单条分支「不再等 <对方>」，仅结算该子分支并向父工作回报明确放弃原因，其余分支照常继续；晚到真实回执标明迟到归档，不重复结算。

### 等待图判环与硬信号无进展暂停

- **等待图判环**：
  - `calls` / `waits(kind='call')` 检测直接或传递等待环（如 `A → B → A` 或 `A → B → C → A`），成环时拒绝新委派并提示改用 `ask_back` 追问或结束本回合自动回传结果。
  - `waits(kind='ask')` 检测互问死锁环，成环时拒绝并引导改用 `ask_user` 交由用户拍板。
- **硬信号无进展暂停（无固定步数上限）**：
  - 移除按跳数、总条数、固定返工次数或文本关键词拦截的旧规则。
  - 在因果链根工作上计算确定性进度签名 `(revision, workspaceDigest, outputDigest, errorSignature)`：当同一未决键连续 3 次采样签名完全不变（无修订、无工作区变更、无新输出/错误变化）时，原子暂停该因果链（`status = 'paused'`），在界面展示暂停卡供用户点击「继续」或「取消」，绝不悄悄丢弃；一旦用户发送新消息、点击继续或产生实质进展，停滞计数立即清零。

## 不做什么

- 不把实时状态写进系统提示（保护提示缓存）。
- 不设全局跳数、消息总量或合法协作返工次数的硬编码上限。
- 不做批量派活的隐式接口，也不给 `request_id` 附加模板语义。

## 已知限制

- 下游若持续等待用户审批或人工输入，上游会保持 `waiting` 直到完成或用户主动放弃/停止；实时状态明确标出等待对象。
- 一个 `request_id` 严格对应一份内容指纹；改动正文需更换新的 `request_id`。
