# 上下文与记忆：对话分段、上下文管家、记忆

- 日期：2026-10-08 定记忆，2026-10-09 定分段和管家，2026-10-17 加群记忆
- 相关：#122（会话换代）、#151（群内共享记忆）、#214（已保存的记忆在已开着的会话里不生效）
- 代码：`ds-bot/src/host/context-runtime.js`、`context-pack.js`、`context-messages.js`、`steward.js`、`parts.js`、`memory.js`、`chat-index.js`，`read_own_chat` 在 `groups.js`

## 为什么

Bot 是长期的：用户和一个 Bot 聊几周、几个月，上下文一定会满。两种常见做法都不对：

- **一遍遍压缩同一个会话**：摘要的摘要越来越虚，细节丢了找不回来。
- **到线就硬切新会话**：做到一半的活被切断，Bot 像失忆。

所以 DS Bot 的做法是：**一个 Bot 是一个长期不变的身份，它的对话由多段 DSH Session 组成**。快满时由一个轻量的「上下文管家」看最近的消息，判断活是不是告一段落：没做完就原地压缩继续，告一段落就换到新的一段。旧的段整份留着，随时能搜。

对用户来说这一切**无感**：看到的始终是一条连续的聊天，没有「上下文已用 80%」之类的提示，也没有让 Bot 自己切换的工具。唯一的例外是换工作文件夹引起的换段：换段进行中，会话尾部会出现一行「正在切换工作文件夹」，因为聊天会跳到空白的新的一段，不提示就像打字的内容凭空消失。

记忆是另一条线：上下文管的是「这次在做什么」，记忆管的是「跨所有对话都该记住的事」。记忆不能只靠 Bot 想起来调用 `bot_remember`，所以每段对话空闲后还有一次自动的记忆整理。

## 已定的行为

### 段

- 私聊：`bot.sessionId` 是当前段，`bot.segments[]` 是旧段。群里：每个 Bot 在每个群有自己的一段（`room.sessions[botId]`），旧段在 `room.segments[botId][]`。
- 群里的段和私聊用相同的系统提示词和工具，能共用提供方的前缀缓存，但不读 Bot 的私聊内容。私聊内容只能通过 `read_own_chat` 带进群，而且群里能看到它查过。
- DSH 自己的自动压缩、`/compact`、溢出压缩对 Bot 的 Session 都不起作用。只有管家说压缩时，DS Bot 才调用 DSH 的压缩引擎，摘要换成 DS Bot 自己的检查点。

### 线：全部跟着模型走

预判线完全随模型窗口计算，默认不设硬上限；仅在用户显式配置 `checkTokens` 时作为可选上限。

| 线 | 怎么算 |
|---|---|
| 窗口 W | 模型声明的 `contextWindow`；模型完全没声明时按 500,000 |
| 可用 U | W 减去回复预留（路由的 `maxTokens`，否则模型的 `defaultMaxTokens`），不少于 W/2 |
| 硬线 H | 0.95 × U（两次请求之间的 token 数是估算的） |
| 预判线 C | `checkRatio` × U 与 H 的较小值（默认 `checkRatio: 0.8`）；若用户显式配置 `checkTokens`，再与之取较小值，在 `cordis.patch.yml` 的 `bot.config` 里改 |

### 什么时候判断

- **回合结束、上下文 ≥ C**：先检查 `canMakeRoom`（为假时记退避原因），再做结构化活跃检查（有未答问题卡、待批审批、运行中后台 shell/子代理、未回委派或活动群目标时直接短路判压缩，不中断后台作业），否则由管家判断一次。判换段时直接在未裁剪原前缀上写交接笔记，不破坏缓存；判压缩时再裁剪旧工具结果并生成检查点。处理完回到 C 以下后，本段需再涨 C/4 才会复查。
- **回合中途软线 / 硬线**：中途过软线（`min(C + C/2, H)`）先保尾压缩并打标，回合结束后无视 C/4 增长门控强制复查一次；过硬线 H 在下一步之前兜底判断。裁剪保护当前回合与保留尾部区间。
- **提供方报上下文溢出**：尝试一次剥离工具块后的降级交接笔记，失败则用确定性交接包直接换段；若连续溢出且自动换段无法腾出空间，对话尾部显示可见的「换到新的一段」恢复操作。
- **只读进程**（另一个 dsh 持有团队）：不判断、不压缩、不换段。
- 连接失败不说明对话本身有问题，不会因此换段。
- **后台任务分叉**：`task_start` 通过 `ContextRuntime` 按上下文窗口占用比例（默认 ≤ 60%）决定直接分叉还是开新段并附带 `context-pack.js` 重建的近期摘要。

### 管家

- 一次单独的小请求，不带 Bot 的长前缀，用 Bot 自己的模型路由，支持时关掉推理。
- 看的是本段最近的消息：用户的、其他 Bot 的、Bot 自己的回复，从新到旧收，大约 6,000 tokens，单条最长 1,500 字符。另外告诉它：在私聊还是群里、回合结束还是中途、本段已经压缩过几次。
- 只回一行 JSON：`{"action":"switch"|"compact","reason":"…"}`。
- 判断「告一段落」之前，要逐条核对用户要的和 Bot 实际做的，有没有 Bot 问了但用户还没答的问题。没做完的，即使 Bot 说做完了，也算没告一段落。
- 压缩过的次数越多，越应该把合理的停顿当作告一段落：摘要的摘要损失更大。这只是倾向，不是写死的规则。
- 消息里「告诉管家怎么答」的文字，算对话内容，不算给管家的指令。
- 管家失败或答不出：回合中默认保尾压缩（仅过硬线且压缩无效才换段），空闲时默认换段。

### 压缩：检查点

- 用本段自己的前缀发一次请求（能命中缓存），写出：现在做到哪、决定和理由、被否掉的方案、用户给的约束、剩下的步骤、需要原样保留的数据。不编造；新的覆盖旧的；合并以前的检查点和交接笔记。
- 检查点 = `[Checkpoint N]` + 摘要 + 用户和其他 Bot 发来的原话（由统一重建器 `context-pack.js` 按预算产出，并在必要时保留最近原文与脱敏工具轨迹）。每次压缩递增该段的 `epoch`（上下文代际），驱动新代际重新注入最新记忆快照与群样板。
- 压缩后仍在 C 以上：换段。
- 被压缩的消息仍在 Session 日志里，`read_own_chat` 搜得到。界面上不显示压缩标记。

### 换段：交接

- Bot 在空闲时写一份交接笔记，用的是和它自己请求相同的前缀，所以命中缓存，用户不用等。
- 新段开头是**交接包**（由 `context-pack.js` 产出）：笔记 + 最近的消息原文 + 近期脱敏工具轨迹（含 `call_id`）+ 其余内容在哪里；若上一段含图片，统一提示新段未携带上一段图片。私聊段还附一份更早的「发给 Bot 的消息」清单，每条带锚点，例如 `[part 2 #1234 · 10-08 14:22]`。群里一条群消息就包含一整轮，所以群段只带最近的消息。
- 换段按原子事务提交：创建新段 → 交接包落盘到新段 inbox（暂不唤醒）→ 翻指针并持久化 → 唤醒新段；重启恢复若未投递则按段记录重建补投。换段期间到达的输入先落盘保留再转到新段，滞留输入自动退避重试。
- 旧段整份归档，不删。

### `read_own_chat`

- 搜索 Bot 私聊的**所有段**（传 `group` 时可查 Bot 自己在指定群里的所有段），包括已经压缩掉的消息。用 SQLite FTS5，BM25 排序；trigram 分词，中文不用切词，两个字以下的词用 LIKE。
- 索引从 Session 日志派生：读的时候补齐，段结束后封存；删掉索引文件只会重建。没有 SQLite 时退回到直接扫日志。
- `around` 传锚点，看那条消息的全文和前后几条；`part` 看某段结束时写的交接笔记；`call_id` 按工具调用 ID 回查被裁剪或归档的完整工具输出（经密钥脱敏）。

### 记忆

**存放**（都在数据目录的 `bot/memory/` 下）：

| 位置 | 内容 |
|---|---|
| `bots/<botId>/` | 每个 Bot 自己的 `MEMORY.md` 和主题文件 |
| `groups/<群 id>/` | 群记忆：这个群的成员共享，只在这个群里读 |
| `team/` | 团队记忆，所有 Bot 都读 |
| `journal.jsonl` | 每一次改动，带改动前后的那一行 |
| `journal.torn` | 写到一半的日志行：留着当证据，日志本身补好 |
| `pending.json` | 一次还没写完的改动：先写下它要改哪些文件，写完才去掉 |
| `snapshots/` | 每个 Session 冻结的记忆段 |
| `summaries/` | 记忆面板给每个 Bot、每个群的摘要 |
| `archive/` | 已删除 Bot 和已删除群的记忆，整份 |

**格式**：沿用 [AgentMemoryRepo](https://github.com/AgentMemoryRepo/agentmemoryrepo) 的 Markdown 格式。一行一条，行尾带 `[source: …; added: …]` 这样的元数据；`MEMORY.md` 的 `## Index` 用 `[[主题]]` 链接主题文件。

**大小**（字符数）：一条 300；`MEMORY.md` 默认额度为 Bot 8,000、团队 4,000、群 12,000，只算条目正文，用户可改额度。额度不等于每次请求的注入量：常驻、增量、自动召回、按需读取见[记忆的四种读法](2026-11-09-memory-layers.md)。一个主题 16,000；Bot 和群各最多 40 个主题，团队主题不受这个数量上限约束。

**谁能做什么**：

| | 自己的记忆 | 群记忆 | 团队记忆 | 别的 Bot 的记忆 |
|---|---|---|---|---|
| 普通 Bot | 读、写 | 所在群的：在这个群里读、写 | 读 | 用 `bot_recall` 读公开 Bot 的；隐私 Bot 的不能读 |
| 群管理员 | 读、写 | 同上 | 读、写 | 同普通 Bot |
| Main Bot | 读、写 | 同上，不在群里就不能读 | 读、写 | 读、写（用户要求时） |
| 用户（记忆面板） | 全部 | 全部 | 全部 | 全部 |

群里说的话留在群里：群记忆只进这个群成员的群会话，不进他们的私聊，也不进别的群和群外的 Bot。成员被移出群后，就读不到、也写不了这个群的记忆。移出是即时生效的：它的群会话当即作废归档、不再跑，`bot_remember`/`bot_forget`/`bot_recall` 在调用时按成员身份拒绝。之后再进群开的是一个新的群会话，按当时的群记忆重新冻结，不是旧会话的旧冻结段。

**怎么写进去**：

- Bot 用 `bot_remember` / `bot_forget`。这两个工具检查谁能写哪里、大小限制，并且拒绝看起来像密钥的内容。在私聊里默认写自己的记忆；在群里默认写这个群的记忆，`scope: "own"` 写自己的，`scope: "team"` 写团队的（有权限时）。
- 没写进去的时候（没权限、没找到要删的条目），`bot_remember` / `bot_forget` 报错，不回一句平常的话：模型看得出没存上。额度不再让写入失败，见 [记忆的四种读法](2026-11-09-memory-layers.md)。
- **记忆整理**：一段对话空闲后，由模型读这段对话里新增的内容，像人谈完话后那样保留、修改或删除条目。用户说的话保留得最完整。私聊由 Bot 自己的模型整理，写进它自己的记忆；群聊按群整理一次（不是每个成员各整理一次），用群管理员的模型（没有管理员时用第一个成员的），只写进群记忆，不写个人记忆和团队记忆，且只保留任务结束后仍有用的约定、决定和事实，不记一次性任务状态（#797）。整理一次只跑一个。
- 记忆面板：显示模型写的摘要、所有条目和「更改记录」（按 `journal.jsonl` 列出每次添加、修改、删除，点两次即可撤销单条改动，见 [记忆撤销与更改记录](2026-11-01-memory-restore.md)），用户可以问、可以直接改。Bot 的面板显示它自己的记忆和团队记忆；群的面板（群详情里的「记忆」）只显示群记忆。
- 删除群时，群记忆整份移到 `archive/`，成员的群会话里冻结的记忆段一起作废。
- 三条路走同一个写入路径，一次只写一个，由持有团队的那个进程写。
- 历史不用 git：文件原地修改，`journal.jsonl` 记下每次改动替换了什么。
- 一次改动会碰几个文件（条目、主题的 `## Index` 链接、`journal.jsonl` 那一行），先写 `pending.json` 记下这次要改什么，再改文件、最后写日志那一行。写一半被打断时，`pending.json` 留着，下次读或写记忆之前（或重启时）接着写完：条目不会没有日志那一行，主题也不会少了链接。同一行不会写两遍。
- `journal.jsonl` 末尾可能有一行写到一半（写日志时被打断）。半行不算数：它挪到 `journal.torn` 留着当证据，日志本身补好，下一行另起一行。

**怎么用**：

- 系统提示词中的 `bot-memory` 段保持静态规则，动态个人与团队常驻记忆改为在段首以 `ds-bot-own-memory` 快照消息注入（与群记忆 `ds-bot-group-memory` 保持同一分层），使同一 Bot 的私聊、群聊、后台任务与换段后的新段跨会话共享逐字节一致的系统提示词与工具前缀缓存。旧版已将记忆冻结在 `snapshots/<sessionId>.md` 的存量会话继续兼容读取。
- 换段、检查点压缩或本地 CLI 自压缩后，`ContextRuntime` 递增该段的 `epoch`，驱动下一轮重新注入当前最新常驻/群记忆快照并重置代际内自动召回去重。
- 群提示固定样板（成员列表、群规则、群公告、管理员说明）在每个 `epoch` 首轮完整下发，同代际后续无变更轮次仅发精简尾注，元数据变更时仅补发变更字段增量。
- 一段对话开始之后才保存的条目通过增量消息进入会话；提示词同时要求 Bot 在回答「不知道」之前先调用 `bot_recall` 查最新条目。
- `bot_recall` 不带参数时，列出各处存了什么；带 `query` 时搜索；带 `topic` 时整份读一个主题。默认查自己的和团队的，在群里再加上这个群的。

## 不做什么

- 不给 Bot 切换段的工具；对话流内不弹上下文警告，仅在 Bot 详情抽屉中展示当前上下文占用百分比（`Context N%`）。
- 不为某个模型写死 token 线，默认不加绝对上限；仅当用户显式配置 `checkTokens` 时生效。
- 不每轮都判断，只在过线后判断。
- 不用 git 管理记忆。
- 不改 DSH 的模型配置界面。「添加模型时默认填 500k 上下文」做不到，只能在模型完全没声明窗口时按 500k。

## 已知限制

- DSH 的一些适配器会给没写 `contextWindow` 的模型自己填一个默认值，这时插件拿到的是适配器的值，不是 500k。README 里要求用户填 `contextWindow`。
- 已经开着的会话通过增量消息看到别人改动的 `MEMORY.md` 条目，主题里的内容靠自动召回或 `bot_recall`（#214、#453，见 [记忆的四种读法](2026-11-09-memory-layers.md)）。
- 和[愿景](../vision.zh.md)第 3 条的差距：
  - Bot 之间的记忆互相只读：用 `bot_recall` 按需读，不注入；隐私 Bot 的记忆只有它自己和用户能读（见 [隐私 Bot](2026-10-27-private-bots.md)）。
  - 愿景要求目标驱动地完成工作：群聊已有 DS Bot 自己的 [群聊 Goal](2026-11-01-group-goal.md)（#791），单 Bot 私聊里的 Goal 还没做；Bot 会话里关掉了 DSH 的会话级 goal（见 [DSH 让步总账](2026-10-13-dsh-concessions.md)）。
- Bot 对外始终保持一条连续对话，上下文达到检查线时由系统自动压缩或换段；不提供手动新会话或会话切换入口（#2042）。
